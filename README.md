# handwritten-gpt

[![CI](https://github.com/aidless/handwritten-gpt/actions/workflows/model-forward.yml/badge.svg)](https://github.com/aidless/handwritten-gpt/actions/workflows/model-forward.yml)

> **English TL;DR**: A character-level GPT written from scratch on pure CPU: attention, FFN, normalization, positional encodings (including RoPE), AdamW, scheduling, and KV cache are all hand-implemented, trained on a Tang-poetry corpus (6.47M parameters, val 4.9938). Run `python train.py --preset tiny`, `python ablate.py`, and `kv_cache_bench.py`. It quantifies structural choices at small compute — ablations over position encoding, depth, and norm placement, plus KV-cache speedups verified bit-identical — while explicitly disclaiming practical generation quality.

**一句话定位**：在纯 CPU 上从空文件手写一个字符级 GPT —— attention / FFN / LayerNorm / 位置编码 / 训练循环 / AdamW / 学习率调度 / 梯度裁剪 / KV cache 全部自己实现，重点不是刷分数，而是「小算力下把结构选择、消融和推理加速量化清楚」。

硬件：AMD Ryzen 7 5800H（8 核 16 线程），**无 GPU**，`torch.set_num_threads(8)`（§8 有理由和实测）。另有一张海光 DCU（16 GB）用于 device 对照，见 §9。

**这个仓能证明什么**：6.47M 参数的字符级 GPT 在纯 CPU 上从零实现并跑通（全唐诗 2,982,529 字、3,000 步、109.6 min、
最终 val 4.9938）；3M 参数消融档里 RoPE（5.3069）优于可学习绝对位置（5.6889）；KV cache 在 50/100/200 新 token 上
加速 2.10× / 2.46× / 2.96×，且贪心解码输出与无 cache 逐 token 位级一致（`torch.equal` 硬断言）。

**这个仓不能证明什么**：这是教学/验证规模的模型——val 4.9938（perplexity ≈148）的输出只在句内连贯，句间是意象拼接，
不能外推到任何有实用价值的生成质量；109.6 min 也不是干净环境，不能当性能基准。§9 的 120M（118.79M 参数、2,000 步、
batch16/ctx512、DCU）是对单卡 16 GB 上限的满程实测，不是与 6.47M 的受控对比（硬件、步数、每步 token 数、epoch 数都不同），
不能据此得出「参数越大越好」；两个量级只能各自内部对照。

## 1. 复现

```bash
pip install -r requirements.txt
python train.py --preset tiny         # 主实验：6.47M 参数 / 3000 步 / 约 110 min（CPU）
python ablate.py --steps 1200         # 三组消融，5 次串行训练
python kv_cache_bench.py --ckpt experiments/tiny/tiny.pt
python bench_micro.py                 # 受控微基准（线程数 / 位置编码 / 深度的 ms/step）
python make_summary.py                # 把 experiments/ 下所有 json 汇成 summary.csv
```

单因素对照（如 RMSNorm）用同一套参数：

```bash
python train.py --preset tiny --norm-type rmsnorm --tag rmsnorm --out-dir experiments/rmsnorm
```

首次运行 `data.py` 会自动下载并构建 `data/corpus.txt`、`data/vocab.json`，之后复用。
代码里没有硬编码的绝对路径，产物全部落在 `experiments/`。

组件与论文的对应（`model.py` 每个类的中文注释都标了出处）：

| 实现 | 对应 |
|---|---|

## 4. 主实验训练结果

配置：batch 12 × 256 token = 3,072 token/step，3,000 步（共 9.216M token，≈3.1 epoch）；warmup 200 步 + cosine 衰减到峰值 lr 的 10%；lr 峰值 3e-4；AdamW(β=0.9/0.95, wd=0.1)；全局梯度裁剪 1.0。

| 指标 | 值 |
|---|---|
| 训练墙钟 | **109.6 min**（纯 CPU，含每 100 步验证）——**非干净环境**，见下方说明，不可横向比较 |
| 训练吞吐 | 1,438 token/s——与上一行同一轮、同一非干净环境下的实测，不代表干净机器上的性能 |
| 最终 val loss（seed 1337） | **4.9938**（perplexity ≈ 148） |
| 最终 val loss（seed 42 复跑） | **5.0205**（与 seed 1337 差 **+0.0267**） |
| 最终 train loss（末 50 步均值） | 5.1573 |
| train_eval loss（关 dropout 在训练集上） | 5.0150 |
| 收敛步数（达自身总降幅 95%） | 2,200（seed 42 同为 2,200） |

loss 曲线：[tiny_loss.png](experiments/tiny/tiny_loss.png)，原始曲线 `experiments/tiny/tiny.csv`；第二 seed 的曲线与 meta 在 `.local_runs/tiny_seed42/`（本地，未入库）。

**关于两轮的墙钟（不可用于比较）**：seed 1337 那轮 109.6 min、seed 42 那轮 **197.1 min**，两轮都不是干净环境（机器上同时有 ollama/llama-server、`embed_abstracts.py`（约 6.5 核）与 GRPO 训练；主实验期 load 11–33，seed 42 那轮实测 load 21–32，8 线程实际只拿到约 4–5 核）。**197.1 min 是外部负载造成的，不是配置或 seed 造成的性能差异**；同理两轮的 1,438 / 800 tok/s 也只能各自对照，不能横向当作性能结论。

**关于两个 seed 的差值（+0.0267）**：该差值小于末段 val 的抖动幅度（末 10 点 std：seed 1337 为 0.0349、seed 42 为 0.0313；相邻 eval 点差 std ≈0.085），判定为**噪声内**；但 **2 个 seed 不足以给出方差与置信区间，这一结论仍属未验证**，不能读作「已验证稳定」。

> val loss（4.994）**低于**训练期 train loss（5.157），但关掉 dropout 后 train_eval=5.015 与 val 几乎重合 —— 差距来自 dropout，不是泛化问题，也没有过拟合（见 §8 理解 1）。

## 5. 生成样例

temperature=0.8，top_k=40，120 token（5 段完整输出见 `experiments/tiny/tiny_samples.md`）。

> **prompt**：`春江潮水连海平`
>
> 春江潮水连海平。天坛何处处，人是故乡心。一水无人不可过，一心知远客还多。山僧有路人间，人事不知秋。一夜来长日月，一年光照晓风。野寺山空路，秋山夜色。竹斋秋月，风落日深。欲过清风，多情不解游。云水何妨去，山深到洛家。风流年夜月，雨雨日寒空。日落南……

> **prompt**：`山中`
>
> 山中。天坛何处处，长是故山云。一水无人不可过，一心知远客还多。山僧有路人知，人事不知秋。一夜来长日月，一年光照月明。野寺山空路，秋山夜色。竹斋秋月，风落日深。欲过清风，多事不归。野鸟喧鸟，村村复深。野水花枝，溪水露秋……

（原始输出里的 `<unk>` 占位符为可读性已删去，见 §8 坑 2。）

结论：五言/七言的分行节奏、意象组合（山/寺/云/月/秋/风）与押韵倾向都学到了；但连贯性只在句内成立，句间是「意象拼接」。两段不同 prompt 出现大段相同句子，说明模型已经背下语料里的高频诗，这是 6.5M / 3 epoch 的容量与数据规模上限，不是解码 bug。

## 6. 消融实验

统一预算（除被消融因素外**完全相同**）：L4 / d192 / H6 / ctx192 / batch16 / 1,200 步 / warmup 160 + cosine / lr 3e-4 / seed 1337 / 同一份数据与验证批。汇总 `experiments/ablations/summary.csv`，曲线 `experiments/ablations/ablation_{pos,depth,norm}.png`。

**墙钟声明（重要）**：消融期间机器上还有别人的 ollama/llama-server 与训练任务，load average 在 11–33 波动，**墙钟只能组内相对看，不能当绝对性能**。为排除干扰，实验结束后我用同一 batch 做了受控微基准（同模型同 batch，只跑前向+反向 15 步取中位数，下称*受控每步*），"每步慢 X%"以它为准。

### 6.1 位置编码：可学习绝对位置 vs RoPE

| 变体 | 参数量 | 最终 val | 首次 ≤5.90 | 实测墙钟 | 实测吞吐 |
|---|---|---|---|---|---|
| 可学习绝对位置 | 3,064,128 | 5.6889 | 600 步 | 1,301 s（21.7 min） | 2,914 tok/s |
| **RoPE** | 3,027,264 | **5.3069** | **400 步** | 1,042 s（17.4 min） | 3,655 tok/s |

受控每步（`bench_micro.py`：8 步/轮 × 3 轮交替顺序取中位数）：learned **749.0 ms** vs RoPE **771.2 ms（+3.0%）**。

**结论：RoPE 少 36,864 参数（-1.2%），val loss 低 0.382（相对 -6.7%），达到 5.90 早 200 步（-33%），代价是每步慢 3.0%。** 两份曲线在 step 800 的差值是 -0.3814、step 1200 是 -0.3820 —— 差距不随训练推进而收敛，说明是整条曲线下移，不是「晚收敛」。实测墙钟里 RoPE 反而更快，是那一轮外部负载更轻（load≈15 vs base 那轮 load≈24）造成的假象，不作为结论。

### 6.2 深度：2 / 4 / 6 层

| 变体 | 参数量 | 最终 val | 首次 ≤5.90 | 实测墙钟 | 实测吞吐 |
|---|---|---|---|---|---|
| L2 | 2,174,400 | 5.8595 | 1,000 步 | 799 s（13.3 min） | 4,749 tok/s |
| L4（基线） | 3,064,128 | 5.6889 | 600 步 | 1,301 s（21.7 min） | 2,914 tok/s |
| L6 | 3,953,856 | 5.6521 | 600 步 | 4,589 s（76.5 min） | 819 tok/s |

受控每步：L2 **460.4 ms** / L4 **761.1 ms** / L6 **1,031.3 ms**。

**结论：L2→L4 val 降 0.171（参数 +41%）；L4→L6 只再降 0.037，却要多 29.0% 参数、每步多 35.5%。** 在 3M 参数、1,200 步预算下加深基本是亏的：同样预算换 RoPE 能降 0.382，换 L6 只降 0.037。L6 的 4,589 s 撞上了 load≈30 的负载尖峰（吞吐仅 819 tok/s），按受控 1,031 ms/step 估算常态约 21 min；收益递减的结论不受墙钟污染影响。

### 6.3 归一化位置：Pre-LN vs Post-LN

| 变体 | 参数量 | 最终 val | 首次 ≤5.90 | 实测墙钟 | 平均 grad norm |
|---|---|---|---|---|---|
| **Pre-LN** | 3,064,128 | **5.6889** | **600 步** | 1,301 s | 1.37 |
| Post-LN | 3,064,128 | 5.8109 | 900 步 | 1,088 s | 0.90 |

**结论：同参数、同步数、同 seed 下 Post-LN 的 val 高 0.122，达到 5.90 晚 300 步（多 50% 步数），末 400 步的验证曲线抖动也更大（std 0.0241 vs 0.0184）。** 注意 Post-LN 这里**并没有发散**（无 NaN，grad norm 均值 0.90 反而更小），所以差距不是「梯度爆炸」，解读见 §8 理解 3。

### 6.4 补做的对照：RMSNorm vs LayerNorm（3000 步，与主实验同配置）

| 变体 | 参数量 | 最终 val | 首次 ≤5.90 | 首次 ≤5.20 | 受控 ms/step |
|---|---|---|---|---|---|
| LayerNorm（主实验） | 6,467,840 | **4.9938** | 500 步 | 1,700 步 | 578.3 |
| RMSNorm | 6,464,768 | 4.9983 | 500 步 | 1,700 步 | **572.9** |

**结论：在这个规模上 RMSNorm 与 LayerNorm 基本等价** —— val 高 0.0045（相对 +0.09%），参数少 256（-0.004%），两条曲线的达标步数完全一致（500 / 1,700），受控每步快 0.9%（在噪声范围内）。训练墙钟 83.4 min vs 109.6 min 的差距**不能归因于算子**：两轮跑在不同时间段，全程 load 在 11–33 间漂移且无逐分钟记录，这两个墙钟数不可直接相减。RMSNorm 少一次均值归约与 bias 加法，其收益要在大模型/GPU 上才会显现，小 CPU 模型上测不出来。

## 7. KV cache

实现：`CausalSelfAttention.forward` 的 `kv_cache` 参数 + `GPT.generate(use_cache=True)` —— 先对 prompt 做一次 prefill，之后每步只喂 1 个 token，把历史 K/V `concat` 进当前步。
**正确性**：贪心解码 20 token，有/无 cache 输出逐 token 完全一致（脚本内 `torch.equal` 硬断言，不是打印提示）。

模型 tiny（6.47M / L6 / d256 / H8 / ctx256），prompt `春江潮水连海平`（7 字），temperature=0.8、top_k=40，每档重复 5 次取中位数：

| 新生成 token | 有 cache | 无 cache | 加速比 | cache tok/s | no-cache tok/s |
|---|---|---|---|---|---|
| 50 | 332.6 ms | 698.4 ms | **2.10×** | 150.3 | 71.6 |
| 100 | 716.5 ms | 1,759.5 ms | **2.46×** | 139.6 | 56.8 |
| 200 | 1,516.5 ms | 4,496.4 ms | **2.96×** | 131.9 | 44.5 |

prefill（7 token）7.35 ms；逐 token 延迟曲线 `experiments/kv_cache/kv_cache_latency.png`。

| 路径 | 前 50 步 | 末 50 步 | 变化 |
|---|---|---|---|
| 有 cache | 6.25 ms/token | 9.92 ms/token | +59% |
| 无 cache | 23.13 ms/token | 22.72 ms/token | 基本持平 |

内存代价：每层每 token K/V = `2 × n_head × head_dim × 4B` = 2,048 B；6 层合计 **12,288 B = 12 KiB/token**。prompt 7 + 生成 200 = 207 token 时约 **2.4 MiB**，相对 26 MB 权重可忽略（进程 RSS 558 MB，主要是 torch 运行时）。

**结论：生成长度 50→200，加速比 2.10×→2.96×。** 无 cache 的单 token 成本随历史长度增长（token 吞吐 71.6→44.5），cache 路径近似恒定（150.3→131.9）；但实测无 cache 的末 50 步延迟几乎不涨（22.72 ms），原因是 ctx=256 太短、CPU 上小矩阵乘的增量被算子调度固定开销淹没 —— 所以**加速比在这里趋于饱和，不会随长度无限增长**（§8 理解 4 有展开）。

## 8. 踩坑与原创理解

**坑 1：CPU 上 `torch` 线程数不是越多越好，16 线程比 8 线程慢 5.0×。**
同一模型、同一 batch（L4/d192/ctx192/B16），只改 `torch.set_num_threads`（受控微基准 3 轮交替中位数）：

| 线程数 | 4 | 8 | 12 | 16 |
|---|---|---|---|---|
| ms/step | 881.9 | **816.4** | 2,510.6 | 4,065.2 |

8 核 16 线程机器上超配线程后，OpenMP 同步 + 线程迁移开销吃掉了全部收益。这是纯 CPU 训练里最容易被忽略、影响最大的一项参数；预设里固定写死 8。

**坑 2：字符级 `min_freq=2` 的 `<unk>` 会被模型学成「万能字」。**
生成样例里 `<unk>` 高频出现。原因很直接：`<unk>` 在训练集中是高频 token，占据大量罕见字的位置，模型学到的是「这里该输出一个稀有字」→ 输出 `<unk>`。这不是 bug，是数据分布的自然结果。重做会用 `min_freq=1`（词表约 1.2 万，embedding 参数翻倍）或在采样时把 id 0 的 logits 置 `-inf`。

**坑 3（DCU）：容器里 `import torch` 报 `librocm_smi64.so.2` 找不到，补一条 `LD_LIBRARY_PATH`。**
现象：`ImportError: librocm_smi64.so.2: cannot open shared object file`。默认 `LD_LIBRARY_PATH` 只含
`/opt/dtk/lib*`，而该库在 `/opt/dtk/.hyhal/rocm_smi/lib`（`/opt/dtk` 是 `/opt/dtk-26.04` 的软链）。
每次上机第一件事：

```bash
export LD_LIBRARY_PATH=/opt/dtk/.hyhal/rocm_smi/lib:$LD_LIBRARY_PATH
```

**坑 4（DCU）：容器内首次 `import torch` 要 1–2 分钟，不是卡死。**
HIP 首次加载要枚举设备、建 kernel 缓存，期间没有任何输出。所以「环境预检」和「正式训练」要尽量
合并成**一个** Python 进程：每多起一个进程，就多付一次这 1–2 分钟，而且很容易误判为挂死而重复起进程。

**理解 1：val loss 低于 train loss 不是泄露，先关 dropout 再下结论。**
主实验 val=4.9938，训练末 50 步 train=5.1573，看似「验证比训练好」；关掉 dropout 在训练集上算得 5.0150，与 val 几乎重合。0.16 的倒挂完全由 dropout 解释。这条直接决定了消融判据必须用 val（且各组 dropout 相同），不能用训练期滑动 loss。

**理解 2：RoPE 的收益主要来自参数共享，而不是「更好的位置表示」。**
RoPE 省掉 192×192 位置表（36,864 参数，-1.2%），val 却低 0.382。字符级中文诗的关键结构是**相对**的：五言/七言的第 2 字与第 4 字构成对仗，这个关系与它是诗的第几行无关。绝对位置表要为 192 个位置各学一个独立向量，样本效率低；RoPE 把位置写成 q/k 的旋转，同样的相对距离在任意 offset 共享参数。代价是每步 +3.0%（每层多两次旋转与 `cat`）。

**理解 3：小模型 + 短上下文下，Post-LN 表现为「学得慢」而不是「训崩」。**
经典叙事是 Post-LN 需要 warmup 才不发散。实测：Pre-LN grad norm 均值 1.37（常被裁到 1.0），Post-LN 仅 0.90（几乎不被裁剪），无 NaN、无发散，但 val 高 0.122、达标晚 300 步、末段抖动更大。我的解释：Post-LN 每层残差主干都要先过 LN，恒等通路被切断，梯度必须穿过 LN 的雅可比，等效步长被压缩；在当前 lr=3e-4 + warmup 配置下表现为「慢」而非「炸」。把 lr 拉到 1e-3 以上我预期才会看到真正的不稳定 —— 这一点本次未验证。

**理解 4：CPU 上小模型的 decode 延迟由固定开销主导，所以 KV cache 的加速比会饱和。**
理论上无 cache 是 O(t²)、有 cache 是 O(t)，加速比应随长度增长；实测 50→200 token 只从 2.10× 涨到 2.96×，且无 cache 的末 50 步单 token 延迟（22.72 ms）几乎不随时间增长。ctx=256、6.47M 参数下，每次前向的 Python/算子调度开销远大于矩阵乘增量，于是两条路径都撞在同一个常数底噪上。要看到接近理论值的加速比，需要更长上下文或更大模型。

**理解 5：加深在这个规模上是负收益，位置编码才是高性价比旋钮。**
L4→L6 参数 +29.0%、每步 +35.5%，val 只降 0.037；而 RoPE 参数 -1.2%、每步 +3.0%，val 降 0.382。同预算下「换位置编码」的收益是「加两层」的 10 倍。这条结论只适用于 3M 参数 / 2.98M 字符 / 1200 步这个区间，不能外推到大模型。

## 9. 加速卡迁移（海光 DCU 16 GB / AMD Radeon 48 GiB）

环境：单卡 DCU，显存 **16,368 MiB**；容器 cgroup **7 CPU / 60 GiB**；DTK 5.7.1、torch 2.9.0+hip 6.3（bf16 可用）；
**无外网**。代码改动只有三处：`--device`/`--dtype` 参数与 `.to(device)`、采样用的 CPU `Generator`
换到当前设备、`evaluate()` 跟随设备。attention/FFN/LayerNorm/AdamW 全是手写，HIP 直接支持。

### 9.1 加速比（只能同配置比）

| 对照 | 配置 | CPU | DCU | 加速比 |
|---|---|---|---|---|
| tiny→tiny | 6.47M / 3,072 token/步（**bs12 / ctx256**） | 2.136 s/步（本机 8 线程，load 11–33） | 0.31 s/步（稳态；全程均值 0.4117） | **≈6.9×** |
| xl→xl | 63.57M / 8,192 token/步 | **46.99 s/步**（同机容器 7 线程） | 1.01 s/步（稳态） | **46.5×** |

**口径**：只有同一配置才能相除。把 xl 的 1.01 s 去比 tiny 的 2.136 s 是跨配置比较（token/步 8192 vs 3072、
参数 63.57M vs 6.47M），不成立 —— 此前写过的「xl ≈ 2.1×」作废；「CPU 侧线性外推 56 s/步 ≈ 55×」也只是
**估算、未实测**，已被 46.99 s/步的实测替代。

**46.5× 的两个独立来源**：按 s/步 47.0 ÷ 1.01 = 46.5；按 tok/s 8,092 ÷ 174 = 46.5（8,192 ÷ 47.0 ≈ 174 tok/s）。
tiny 那行是 **bs12 / ctx256**（3,072 token/步），不是 bs16 / ctx512：0.31 s/步 是 step 100→300 的**稳态**，
对应 ≈**9,910 tok/s**（3,072÷0.31）；**全程 300 步均值 0.4117 s/步** 才对应 meta 的 **7,461 tok/s**（含 33.6 s 首步）。
这两组数各自自洽，不能交叉配对。

**xl 的 CPU 分母不是本机**：xl fp32 常驻 RSS 8.3–8.4 GB，本机总内存 15.3 GB 且被其他任务占去大半，
4 次尝试都被内核 OOM 杀（`rc=137`、`memory.events: oom_kill 1`），所以退到**同一台 DCU 机器的容器 CPU**
（Hygon C86 7380，7 核上限，loadavg 8.2–8.7，进程 531% CPU / RSS 18.2 GB）。这条分母自带轻微争用、
且 CPU 型号不同于本机，因此「46.5×」是**同一台机器内的 device 对照**，不含跨机差异。

### 9.2 显存档位与 16 GB 天花板

| 档 | 层 / d | 参数 | 稳态 s/步 | tok/s | 峰值显存 / 16,368 MiB |
|---|---|---|---|---|---|
| xl | 12 / 640 | 63.57M | 1.01 | 8,092 | 9,213（56%） |
| xl120m | 16 / 768 | 118.79M | **1.40** | **5,730** | **13,263（81%）** |
| 18 层 | 18 / 768 | 132.97M | ~1.5 | 4,785 | 14,832（91%） |
| 19 层 | 19 / 768 | 140.0M | — | — | **OOM**（已分配 14.55 GiB） |
| 20 层 | 20 / 768 | 147.1M | — | — | **OOM**（15.24 GiB） |

batch 16 / ctx 512 全程不变，**没有靠调 batch 硬凑**。118.79M→132.97M 每 +1M 参数约 +111 MiB，
内插得 **16 GB 的天花板 ≈ 135M 参数**。判死规则：**OOM 或稳态 s/步 > 3 s 就不扩**；120M 两条都不触发，
**已按规则跑满 2000 步**：`train_wall_clock_s=2,859 s（47.7 min）`、总墙钟 2,926.9 s（48.8 min）、
`final_val_loss=4.4603`、`diverged=false`，1400→1900 步 tok/s 5,658→5,721 **没有降速**。

**口径**：上表 `s/步` 是稳态（xl 取 200→2000；120M 取最后 100 步增量中位），`tok/s` 是 **meta 的全程均值**（`tokens_per_s`，含首步预热与 eval），两者不是同一段，不能交叉配对。同口径换算：xl 稳态 1.01 ↔ ≈8,111 tok/s，全程均值 1.0124 ↔ 8,092；120M 稳态 1.40 ↔ ≈5,851，全程均值 1.4297 ↔ 5,730；133M 的 4,785 是 25 步含预热均值（≈1.71 s/步），稳态 ~1.5（≈5,461）。

### 9.3 已知代价：没有 `--resume`

`train.py` **没有 `--resume`**，`{tag}.pt` 只在全部步数跑完才写；中途崩只能同 tag 重跑（覆盖 csv/pt/meta）。

**规则（写死，按实测定的阈值）**

- **单次实验不加 `--resume`**。依据：实测最长单轮是 **498.43M / 2000 步 / batch 16 / ctx 512**，总墙钟 **2,891.6 s（48.2 min）**，其中纯训练 2,173.7 s（36.2 min），差额来自 20 次验证与收尾采样；低于「单轮 ≥1 h」阈值，重跑成本（≈0.8 GPU 小时）小于改动主训练路径（optimizer/step/RNG/CSV 追加恢复）带来的回归风险。DCU 侧同口径依据：120M / 2000 步实测 47.7 min 训练、48.8 min 总墙钟。
- **例外触发（满足任一才补「每 N 步原子写 + `--resume`」，且先在 CPU 上验证恢复正确性）**：① 出现**非我方原因的 kill/OOM**（机器被回收、同机第三方任务抢显存等）；② 要**连跑 ≥3 次 500M 档**扫描。

### 9.4 第二张卡：AMD Radeon Cloud / gfx1100 / 48 GiB

环境：`amd-oneclick-base` 镜像，ROCm **7.2.1**、torch **2.9.1+hip 7.2.53211**；容器 cgroup **16 CPU / 55 GiB**（宿主 `nproc`=128、`free` 报 503 GiB，**虚高 8× / 9.1×**，以 cgroup 为准）；`/workspace` 为 98 G loop 挂载（可用 84 G），`/tmp` 只有 4 G。GPU 铭牌读不出型号（`AMD Radeon Graphics`，DID `0x744b`），按 **96 CU + 48 GiB** 推定为 W7900 级；PwrCap 241 W、满载实测 232 W、SClk 2181 MHz。代码零改动，仅 `--device cuda --dtype bf16 --threads 16`。

口径：batch 16 / ctx 512 / bf16；标「探测」的档跑 100 步，标「满程」的跑 2000 步。**DCU 与本卡分列，不做同列混算**。

**天花板**（以下均指**不开激活重计算**）：DCU 内插 ≈135M；本卡**实测** 548.82M 可跑、599.20M OOM，边界落在 **(548.82M, 599.20M)**，中值 ≈0.57B。549M 档峰值 46.90 GiB、余量仅约 1.1 GiB，**不建议当稳定工作点**。此前「线性拟合 0.56B」的估算已被这组实测取代（数值接近，但性质从估算变成实测区间）。开启 `--grad-ckpt` 后上限**未测**（498M 峰值 44,035 → 10,980 MiB），不能把 0.57B 当成「这张卡能跑多大」的答案。

### 9.5 本卡可复用的坐标（2026-11-07 实测）

以下三条只对本卡（gfx1100 / 48 GiB / ROCm 7.2.1）与「batch 16 · ctx 512」成立，换卡或换 batch 需重测。

**① 步数预算 ↔ 语料量（决定「加数据」还有没有用）**
每次实验 2000 步 × 16 × 512 = **16.384M token**。同一份 wiki 语料切前缀（同验证集、同 vocab V=11519、同 seed 1337）：

| 语料字符 | 训练 token | 覆盖 epoch | final_val |
|---|---|---|---|
| 52,641,486 | 51.7M | 0.31 | **4.0285** |
| 104,252,289 | 104.4M | 0.157 | 4.0425 |
| 182,999,743 | 183.3M | 0.089 | 4.0508 |

→ **固定 2000 步时，语料超过 ≈50M 字符后继续加数据不再降低 val**（反而 +0.014 / +0.022 nats）。原因是 token 预算被摊薄、每 token 见到次数下降，不是数据质量变差。要用更多数据，必须同步加步数（把 16.384M token 保持到 ≥0.5 epoch 需把步数拉到 ≈3,000–6,000 步）。

**② 参数幂律斜率（同预算横切，不是收敛后的 law）**
corpus2 + 同一验证集 + 2000 步，3 档：66.78M → 4.1312、122.65M → 4.0285、302.03M → 3.8856。
`ln(val)` vs `ln(N)`：**斜率 −0.0406**、95% CI [−0.0452, −0.0360]、R² 0.9999。
→ 工程上用 **每翻倍参数 val × 0.9723（−2.77%）**。

三条限制必须一起引用：**(a) 只有 3 点，R² 0.9999 是「3 点必过」的假象；(b) 全部是 2000 步未收敛的横切（conv95 都在 1500–1600 步），不是 Chinchilla 类指数；(c) 区间代入 1B 会跨 ~0.3 nats，不能外推 1B 以上。**

同时：**503.6M 档（L39/C1024/H16, V=11519）在本卡当前占用下 OOM** —— 宿主常驻占 4.59 GiB，torch 到 40.87 GiB 即失败（该档此前峰值 43.6 GiB 能过）。不缩 batch/ctx 硬凑。

**③ KV 池 ↔ 并发（Qwen2.5-0.5B，`gpu_mem_util=0.85`，`TRITON_ATTN`）**
`Available KV cache memory: 37.97 GiB`、`GPU KV cache size: 3,317,776 tokens` → **每 token KV = 11.73 KiB**（≈12 KiB，与 2×24层×2kv_heads×64head_dim×2B 的公式吻合）。

| ctx | 每请求 KV | 理论最大并发 |
|---|---|---|
| 512 | 6.0 MiB | **6,480** |
| 2048 | 24.0 MiB | **1,620** |
| 8064 | 94.5 MiB | 405 |

实测（ctx 512 / 并发 1024）聚合 **18,455 tok/s**、单请求 18.0 tok/s；并发 256 时聚合 12,263、单请求 47.9 —— **聚合与单请求必须分开记**。
`gpu_mem_util` 0.90 / 0.95 **在本机启动即被拒**（`Free memory … less than desired GPU memory utilization`，可用 42.19 / 40.44 GiB），原因是宿主占卡，**0.85 是当前实际上限**。

**④ 7B 微调坐标（Qwen2.5-7B-Instruct，LoRA r=16，bs1 / seq 1024 / bf16）**
加载 **9.3 s**、**0.494 s/步**（2,071 tok/s）、**峰值 20,631 MiB**、可训练参数 40.37M。显存余裕很大，瓶颈是 bs1 利用率不足。下载 hf-mirror 单连接 **28.4 MB/s**（15 GB 全程 25 s）。

## 10. 局限与未完成

- **墙钟受外部负载污染**：消融期间机器上有其他人的 ollama（646% CPU）与三 seed 训练任务，load 11–33；因此墙钟只做组内相对比较，另用受控微基准支撑「每步慢 X%」。主实验两轮同样不是干净环境：seed 1337 为 109.6 min（load 11–33），seed 42 为 **197.1 min**（实测 load 21–32，8 线程实际约 4–5 核）。**197.1 min 由外部负载造成，不是配置或 seed 造成的性能差异**；两轮 tok/s（1,438 / 800）因此也不能横向比较。
- **xl 的 CPU 基线不是本机 8 线程**：xl fp32 常驻 8.3–8.4 GB，本机（15.3 GB，其余任务占大半）4 次被内核 OOM 杀（`rc=137`），分母只能取同一台 DCU 机器的容器 CPU（7 线程、loadavg 8.2–8.7、Hygon C86 7380）。所以 §9.1 的「46.5×」是**同机 device 对照**，不能当作本机 8 线程的绝对值。
- **无 `--resume`**：`.pt` 只在全部步数跑完时落盘，中途崩溃没有可用 ckpt，只能同 tag 重跑（见 §9.3）。
- **两个 seed，仍不给方差/置信区间**：主实验已跑 seed 1337（val 4.9938）与 seed 42（val 5.0205），差 **+0.0267**；该差值小于末段 val 抖动（末 10 点 std 0.0349 / 0.0313，相邻 eval 点差 std ≈0.085），判定为噪声内——但 2 个 seed 不足以给出方差与置信区间，仍属**未验证**。「RoPE 好 0.38」等消融结论依旧只有 seed 1337 的单点估计，没有置信区间。
- **规模限制**：2.98M 字符 / 6.47M 参数 / 3.1 epoch，生成结果的句间连贯性差是规模上限。
- **未做**：正弦位置编码作为第三种对照（`SinusoidalPE` 已实现但未训练对照）；top-p / repetition penalty 等采样改进；长上下文（ctx ≥ 1024）下的 cache 显存-速度权衡 —— ctx=256 时 cache 仅 2.4 MiB，体现不出压力。
- **未做：≥5 个 seed**：目前只有 2 个 seed，无法估计 seed 间方差、也给不出置信区间。**触发条件（写死）**：一旦某条结论要用到 seed 间差异（例如「某配置比另一配置稳定/更好」），就必须把该配置补到 **≥5 个 seed** 才能下结论；未补齐前只能报单点值与「噪声内/未验证」。
